# 01: 对冲逻辑的有效性需要持续验证（此前误判为「死代码」）

**背景**：此前（2026-10-25）在同一段代码上测得「10 路并发 9 路正常、1–2 路卡到 25s」，
并据此在 `mail/115` 里向 Octave 集群报告「EdgeOne 的 `AbortController` 无法中断已发起的
fetch，对冲在中间件内不可行」。

**2026-10-31 复测结果与上述结论相反**：

```
20 次单发（当前真实 bundle）：
  1.50 1.44 1.55 1.35 1.11 1.35 1.13 4.75 2.04 1.56
  1.36 1.77 1.32 1.50 2.48 1.92 1.16 1.56 1.87 2.97  （秒）
⇒ 20/20 全部正常返回，最慢 4.75s，**没有一次卡到兜底上限**
```

**两种可能，都需要进一步分辨**：

1. **对冲确实在起作用**：`win()` 是「首个成功者胜」，第一发卡住时第二发成功即提前返回，
   把原本的 25s 卡顿压到 <5s。兜底 17.5s 从未触发。
2. **当时那次测量的环境不同**（部署未生效 / 网络状况差异），代码本身没变。

**Settling:** 不存在 —— **第一交付物是一个可复跑的并发探针**（`scripts/probe-edge.sh`）：
跑 N 路并发同 URL，记录每次耗时与状态码，输出 >10s 的次数。判据：
- 若 >10s 次数为 0 ⇒ 对冲有效，保留代码，并在 `mail/115` 的勘误里更正；
- 若稳定复现卡顿 ⇒ 回到「死代码」判断，删除对冲段。

**一条已知的边界**（这条不受上述结论影响）：既然实测到对冲有效，那么
`mail/115` 里写给 Octave 集群的「**禁止在 EdgeOne middleware/worker 内做对冲**」是**错的**，
必须更正 —— 否则会把唯一有效的抗抖动手段禁掉。

**Status:** ready-for-agent
